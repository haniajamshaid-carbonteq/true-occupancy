## Background

These changes implement three of five action items from the **July 30, 2026 Halcyon <> Carbonteq weekly call** (Jim McGowan + Erin Walker for Halcyon; Waseem, Aayan, Hammad, Hania, Ali for Carbonteq).

**Who is the real user?** Not just city code-enforcement officers — the driving customer is **mortgage lenders and GSEs** (Freddie Mac, Fannie Mae) verifying whether a property declared owner-occupied on a loan is secretly being rented. This is fraud/compliance checking done pre-close and post-close. The prototype persona ("J. Marlow, Asheville") is illustrative; the real buyer is lending compliance.

**Why this matters for the UI:** Lenders differ in risk tolerance — DSCR/investment-property lenders tolerate gray-area matches more than agency lenders selling to Freddie/Fannie. That means thresholds, outcome rules, and re-scan cadence all need to be configurable per organization, not hardcoded.

## Action Item #1 — Org-scoped caching with stale-report notice

### Meeting context

AI reports are expensive. Halcyon confirmed that reports may be **reused across organizations** to save cost (no compliance issue). But the UI must **never reveal cross-org reuse** — the timestamp must read "first served to your organization," never "we ran this for someone else." Once a report ages past a configurable threshold (~30 days floated as default), the user needs a visual nudge + one-click re-run.

### What we built

A canonical freshness indicator that appears on every scan result and AI report, replacing the old "Generated on" line. When a report exceeds the org's freshness window, the component shifts from informational to actionable.

### Flow

1. User opens a scan result (from Dashboard, History, or Batch detail)
2. `ServedStamp` reads the served timestamp from sessionStorage (set by the entry point that navigated here)
3. Component shows: **"Updated Jul 29, 2026 (4 days ago)"**
4. If the report age exceeds the org's `freshnessWindowDays` (configurable in the admin panel, see Action Item #3): the line renders with a subtle warning treatment + a **"Run New Report"** CTA
5. Clicking re-run clears the cached timestamp and triggers a fresh scan

### Screen-by-screen changes

**`src/components/result/ServedStamp.tsx`** — New component
- Shows `Updated [date] ([relative age])` as a single canonical timestamp
- Listens for a custom `halcyon:served-updated` event so it live-updates if a re-run completes while the page is open
- Falls back to "now" if no served timestamp exists (fresh scan, never cached)
- Reads from sessionStorage so the entry point controls what date is shown — this is how cross-org reuse stays invisible

**`src/components/result/ConfidenceHero.tsx`** — Added ServedStamp
- Placed directly below the verdict score and confidence percentage
- Every single-scan result page now shows the freshness line without any per-screen wiring

**`src/components/result/AIInvestigator.tsx`** — Replaced "Generated on" with ServedStamp
- The old `formatReportDate(generatedAt)` line said "Generated [date]" — that language leaks internal processing. "Served" / "Updated" is intentional: it frames the timestamp as when the org received it, not when Halcyon's pipeline ran it
- ServedStamp sits in the same position (below the case archetype title, above the digest stats)

**`src/pages/HistoryScreen.tsx`** — Stamps served date on navigation
- When a user clicks a history row, derives `resultServedAt` from the row's `scannedAgo` field and writes it to sessionStorage
- Old rows (e.g. "46 d ago") produce a stale ISO date, so the result page correctly shows the freshness warning
- Also clears `resultCached` to prevent stale state from a previous navigation leaking through

**`src/pages/HomeScreen.tsx`** — Clears stale timestamps
- When navigating from the dashboard's "Recent Scans" (which are always current), clears both `resultServedAt` and `resultCached` from sessionStorage
- Prevents a fresh scan from inheriting a stale timestamp left by a previously-opened old report

### Edge cases still to handle

- Exact threshold comparison (> vs >=) for the freshness window cutoff
- What happens when the re-run CTA is clicked but the backend returns the same cached report (needs a "still current" confirmation state vs. an actual refresh)
- Timezone handling — `formatUsDateTime` uses the browser's local timezone; lenders in different timezones viewing the same org report may see different relative ages
- Batch-level freshness — currently no ServedStamp on BatchDetailScreen (deliberate: "first served" is a per-report signal, not a batch-level one), but this decision should be confirmed with Halcyon

## Action Item #3 — Client-side admin panel with configurable thresholds

### Meeting context

Different lenders have different risk tolerance. Halcyon wants an **admin panel with configurable per-organization occupancy thresholds** (what counts as "rented" vs. "not rented"), designed as an extensible place to drop in future client-configurable settings. The admin permission model follows Bob's pattern from TrueTax: admin is a **permission on top of a role**, not a separate role.

### What we built

A full Scan Configuration screen with three sections: confidence thresholds, the outcome matrix (what a finding means given the declared intent), and recurring-scan cadence. Role-gated to Staff Admin only. Also added a demo role switcher so the developer can preview what each role sees.

### Flow

1. Staff Admin clicks **Configuration** in the side nav (pinned above the profile block)
2. Three config sections render as Cards:
   - **Confidence thresholds** — two sliders/inputs defining where "not rented" ends and "rented" begins (the gap between them is "possibly rented"). Clamped 0–100, validated so lower < upper
   - **Outcome matrix** — for each declared intent (owner-occupied, second home, rental, not sure), what status (green/yellow/red) does each verdict (not rented, possibly rented, rented) produce? Edited as ChipRows per intent category
   - **Recurring scans** — cadence for red-flagged properties, freshness window in days (this is the threshold ServedStamp uses)
3. Any edit shows a sticky "unsaved changes" footer with Save/Discard
4. Non-Staff-Admin users see a locked empty state ("You don't have permission to change these settings")

### Three-layer model (important for the developer)

The occupancy config has three layers that apply in order:

1. **`defaultIntent`** — what we assume when nobody declares anything (defaults to "not sure")
2. **`thresholds`** — where confidence stops being one verdict and becomes the next
3. **`outcomeMatrix`** — declared intent x verdict = status (green/yellow/red)

A scan stores only two things: the raw `confidence` and the `configVersion` in effect when it ran. Verdict and status are derived at read time — so editing a threshold today never rewrites a report a lender already attached to a closing file.

### Screen-by-screen changes

**`src/pages/ScanConfigScreen.tsx`** — New screen
- Three `ConfigSection` cards (thresholds, outcome matrix, recurring scans)
- Input clamping: confidence 0–100, freshness window 1–365 days
- Dirty-state tracking with a sticky footer (Save / Discard)
- Props for spec frames: `forceDirty`, `seedInvalid`, `defaultOpenIntent` allow the states-spec to render every visual state without interaction

**`src/state/OccupancyConfig.tsx`** — New state module
- Exports all vocabulary: `OCC_INTENTS`, `OCC_VERDICTS`, `OCC_STATUSES` with human labels and short forms
- `DEFAULT_OCC_CONFIG` — the org's default config, used everywhere as the fallback
- `occThresholdError()` — validates that lower < upper
- `occThresholdsFor()` — resolves per-category overrides with fallback to global
- Naming: everything prefixed `OCC_` / `Occ` to avoid collisions in the shared global scope (no bundler)
- **Three colour layers are deliberately distinct** (this is a common mistake): verdict tones (categorical, non-judgemental: not-rented / possibly-rented / rented) ≠ status (green/yellow/red = contradiction severity) ≠ the existing clean/warn/risk palette. The status layer maps to clean/warn/risk for rendering, but verdict tones are never coloured directly

**`src/components/SideNav.tsx`** — Added Configuration link
- "Configuration" not "Preferences": these are org-wide rules that change how everyone's scans are scored, not personal settings
- Pinned above the profile block (not in the primary nav group) — it's a destination you visit occasionally, not part of the daily scan workflow
- Role-gated: reads `role` from `AppStateContext`, only renders for `'staff'`

**`src/pages/ProfileScreen.tsx`** — Added demo role switcher
- "View as" card with Staff Admin / Admin / User options
- Switching to Admin or User hides the Configuration nav link
- Demo-only (no real auth) — lets the developer preview the role-gated behavior without backend RBAC

## Red Addresses — properties where scan contradicts declaration

### Why this exists

This is the natural consequence of Action Item #4. Once you compare declared intent vs. observed reality, some properties won't match. These are "red" — not a judgment of good/bad (the design system is deliberately **verdict-neutral**: "rented" is a finding, not a failure), but a factual contradiction. A property declared owner-occupied that scans as rented is red. A property declared as rental that scans as rented is green.

Red addresses get **automatic recurring scans** (monthly, configurable in the admin panel). An operator can stop the re-scan but **cannot "clear" the red status** — a red finding is a fact in the record, not something you dismiss. An earlier design had a "clear" action; it was removed.

### Flow

1. A batch scan completes. The reconciliation engine checks each row's verdict against the batch's declared intent using the org's outcome matrix
2. Rows that resolve to `red` status are flagged
3. The system auto-creates a monthly recurring scan for each red address
4. Red flags appear everywhere that address shows up: History, Scheduled, Dashboard, Batch detail, Scan context bar
5. An operator can open the Red Property Drawer, stop the recurring scan (with a reason), or restart a stopped one
6. Stopping says "the finding stands, stop re-checking" — the property stays red in the record

### Screen-by-screen changes

**`src/pages/RedAddressesScreen.tsx`** — New screen

- Every row is red by definition, so there's no color column — the width is spent on the mismatch detail (declared vs. found)
- Clicking a row opens the Red Property Drawer
- Empty state handles both "no red addresses" (good news) and "filtered to nothing" (different message)

**`src/components/red/RedPropertyDrawer.tsx`** — New detail drawer

- **Stop mode:** Confirmation with a required reason textarea — "Why are you stopping recurring scans?" Creates an audit record
- **Done-stop / Done-restart:** Success confirmation with the action taken

## Re-scan & Re-run AI report (batch row actions)

### Why this exists

A completed batch row can go stale or fail for a transient reason (geocoder timeout, rate limit). The user needs to **re-scan a single property** without re-running the entire batch, and separately **re-run just the AI report** on a row without re-scanning the listing data. These are two independent lifecycles — the listing scan and the AI report — and each needs its own re-trigger.

### Flow

**Re-scan a row:**
1. User clicks re-scan on a completed or failed batch row
2. `rescanBatchRow(id)` resets the row to `queued` (clears score, risk, listings, AI report — full reset)
3. The batch status flips back to `running`, and the row re-enters the scan queue
4. On completion, `lastScanAt` is stamped with the current epoch

**Re-run AI report only:**
1. User clicks re-run AI on a completed row (listing data stays intact)
2. `rerunRowAIReport(rowId)` sets just the AI report to `running` without touching the listing scan
3. If no AI phase was active, one is created; if one was already running, the row joins it
4. On completion, `lastAIReportAt` is stamped

### Screen-by-screen changes

**`src/state/AppState.tsx`** — Two new actions
- `rescanBatchRow(id)` — full row reset: strips everything back to `{ id, address, status: 'queued', intent }`, kicks batch to `running`
- `rerunRowAIReport(rowId)` — AI-only re-run: keeps listing scan data, sets `aiReport.status` to `running`, ensures the batch has an active `aiPhase`
- `lastScanAt` (epoch ms) stamped on listing scan completion
- `lastAIReportAt` (epoch ms) stamped on AI report completion
- These timestamps feed ServedStamp and future freshness calculations at the row level

**`src/spec/MockAppStateProvider.tsx`** — Stubbed new actions
- `rescanBatchRow` and `rerunRowAIReport` as noops for spec frame rendering
- Also stubbed `role`, `setRole`, `isRedStopped`, `setRedStopped` for the role-gating and red-address features

## Timestamp migration: `scannedAgo` → `scannedAt` (epoch ms)

### Why this change

The entire data model used human-relative strings like `'8 min ago'`, `'Yesterday'`, `'6 mo ago'` as the timestamp for history entries and schedules. This was fine for static mocks but broke three things:

1. **Freshness calculations** — ServedStamp needs to compute "is this report older than N days?" That requires a real date, not a string you have to reverse-parse with regex (`scannedAgoToHours` was a 15-line parser that guessed based on the label and drifted every time the page was open)
2. **Certificate PDF** — `CertificateSheet` had its own duplicate parser (`certParseScannedAgo`) doing the same reverse-engineering. Lenders archive these PDFs for years; "8 min ago" is meaningless by then
3. **New scans** — `addSingleScanToHistory` creates entries at runtime with `Date.now()`. Mixing epoch numbers and relative strings in the same array is a type error waiting to happen

The fix: every `scannedAgo: string` is now `scannedAt: number` (epoch ms). Every `createdAgo: string` is now `createdAt: number`. A single `seedTime('8min')` helper generates epoch timestamps for seed data. All consumers format at render time.

### Screen-by-screen changes

**`src/state/AppState.tsx`** — Data model migration
- `SingleHistoryEntry.scannedAgo` → `scannedAt: number`
- `BatchHistoryEntry.scannedAgo` → `scannedAt: number`
- `SingleScheduleEntry.createdAgo` → `createdAt: number`
- `BatchScheduleEntry.createdAgo` → `createdAt: number`
- New `seedTime(offset)` helper: `seedTime('8min')` → `Date.now() - 8 * 60_000`. Used for all seed data so timestamps are always relative to "now" rather than hardcoded ISO strings
- Added `configVersion` to `SingleHistoryEntry` — stores the `OccConfig.version` in effect when the scan ran, so verdicts can be re-derived against historical thresholds, not whatever's current
- Deleted `scannedAgoToHours()` and `formatScannedDate(scannedAgo)` reverse-parsers

**`src/pages/HistoryScreen.tsx`** — Consumes epoch timestamps
- Deleted the `scannedAgoToHours` regex parser (was duplicated from AppState)
- `formatScannedDate` now takes a number, not a string: `new Date(ts).toLocaleDateString(...)`
- `scannedIso()` reads `row.scannedAt` directly instead of reverse-parsing a label
- All table columns and sort comparisons use the numeric `scannedAt`

**`src/components/result/CertificateSheet.tsx`** — Simplified
- Deleted the entire `certParseScannedAgo` function and its `CERT_HISTORY_UNIT_MS` lookup table (~20 lines removed)
- Replaced with a one-liner `certParseScannedAt(ts: number): Date` that just wraps `new Date(ts)`
- History rows on the certificate PDF now read clean calendar dates from real timestamps

**`src/spec/StatesSpecApp.tsx`** — Updated spec seed data
- `SAMPLE_HISTORY` and `SAMPLE_SCHEDULES` use `seedTime()` instead of string labels
- `scannedAgo` → `scannedAt`, `createdAgo` → `createdAt`

## Re-scan flow on result page (ConfidenceHero)

### Why this exists

A user looking at a scan result needs to be able to re-run it right there — without navigating back to the scanner, re-entering the address, and waiting through the intake flow again. This is especially important for the stale-report case: ServedStamp shows "this report is 46 days old" with a warning, and the natural next action is "re-scan now." The button needs to be right next to that warning, not buried in a menu.

### Flow

1. User is on a result page (clean/medium/high), sees the ConfidenceHero with the verdict score
2. A small re-scan icon button sits next to the score/verdict area
3. Hover shows a tooltip: "Re-scan this property"
4. Click opens a **confirmation popover** (not a modal — it's lightweight, anchored to the button):
   - Shows "Re-scan this property" as the title
   - If a previous served timestamp exists, shows "Last report served [date]" for context
   - Cancel / Continue buttons
5. Clicking **Continue** starts the re-scan:
   - Button enters a spinning/loading state
   - Dispatches `halcyon:rescan-start` event
   - After 2.2s (simulated scan time), updates `resultServedAt` in sessionStorage to now, clears `resultCached`
   - Dispatches `halcyon:served-updated` (ServedStamp listens for this and live-updates)
   - Dispatches `halcyon:rescan-end`
   - Button returns to idle

### Screen-by-screen changes

**`src/components/result/ConfidenceHero.tsx`** — Re-scan button + confirmation popover
- New `RescanButton` sub-component (~100 lines): icon button with tooltip on hover, confirmation popover on click, loading spinner during re-scan
- Confirmation popover shows last-served date for context, with Cancel/Continue actions
- Popover dismisses on outside click (overlay pattern)
- On confirm: updates sessionStorage, dispatches custom events so ServedStamp and any other listeners update without a page reload
- Disabled state with reason tooltip when a re-scan is already running

## Fresh scans auto-create history entries

### Why this exists

Previously, running a scan from the home screen search bar didn't create a history entry — the scan result appeared, but if you navigated away, it was gone. History only contained seed data. Now every fresh scan creates a real history record with a proper timestamp, so the History screen reflects actual usage.

### Flow

1. User enters an address on Home, clicks Scan
2. ScanMidScreen animates the scan steps (3.2s)
3. On completion, `addSingleScanToHistory` is called with the address, scenario, platform count, and optional reference
4. A new history entry is created with `scannedAt: Date.now()` and `configVersion` from the current org config
5. The entry's `id` is stored in sessionStorage as `scanHistoryId` so re-opening the same result doesn't create duplicates
6. User navigates to the result page; the entry is now in History

### Screen-by-screen changes

**`src/pages/ScanMidScreen.tsx`** — Creates history entry on scan completion
- Calls `addSingleScanToHistory(address, scenario, platforms, reference)` inside the completion timeout
- Guards against duplicates: only creates if no `scanHistoryId` in sessionStorage (re-opening from history sets this)
- Stores the returned `id` in sessionStorage for the duplicate guard
- Counts platforms from the scenario's listings data

**`src/state/AppState.tsx`** — New `addSingleScanToHistory` action
- Creates a `SingleHistoryEntry` with `Date.now()` timestamp and current `configVersion`
- Prepends to the history array (newest first)
- Returns the generated `id` so the caller can store it

## What's next

Starting on **Action Item #5 — Image-matching / parcel-ID disambiguation research**. This is the hard unsolved problem from the call: how to confirm a specific unit/property match when a neighborhood has repeated floor plans. Candidate approaches:
- Cross-reference municipality parcel ID (exists in the property-tax Postgres table) against listing coordinates
- Automated image matching (~$1/property, too expensive for batch scale — exploring cheaper alternatives)
- Bounding-box "negative check" (compare candidate counts in a small radius against what's actually listed)
- Google Street View / Realtor exterior photos as fallback when listings lack exterior shots

This is research and feasibility — no UI work expected yet.
